## 要更新哪些服务

以下是**从完整 alpha.8 升级**的范围，不代表这些改动尚未在你的生产环境分批部署。
先核对已部署的 commit 和 Goose 状态，不凭“刚发布了一个 tag”重复迁移。

| 服务 | alpha.8 → alpha.9 | 原因 |
| --- | --- | --- |
| Nav Web | 重建并部署 | 资源/Hero、Tag 消费、#124 appearance 与运行修复 |
| Nav Backend (`gf-nav`) | 更新 | #112 public Hero catalog 与 fixed-ID 请求解析 |
| Game Backend (`gf-game`) | 更新 | Tag Domain 查询、推荐算法及私有 rebuild 命令 |
| Game Collector (`gf-game-collector`) | 随 Tag Domain 协同更新 | 新 Game schema/sqlc 模型 |
| Admin (`gofurry-admin`) | 重建嵌入 React 的完整二进制 | 编辑器/400 字校验、Tag 管理、CloudOps scheduler |
| Nav Collector / Uptime | 本版本无需因产品变更更新 | alpha.8 以来这两个生产模块没有代码变化 |

如果 #113–#122 已经部署且 `gfg` 已到目标版本，后续 #124 部分只需重建 Nav Web。
本记录不声称已核实生产数据库或已部署二进制。

## 数据库与部署顺序

alpha.8 之后仅新增两条 `gfg` Goose migration：

| 版本 | 作用 |
| --- | --- |
| `20260916010000` | `gfg_game.info` / `info_en` 扩为 `varchar(400)` |
| `20260916020000` | 不可逆 Tag Domain 迁移；保留叶子 ID，角色关系补齐，清空旧推荐，current projection 升为 v2 |

`gfn` / `gfa` 没有本版本新增 migration。#112 复用现有 Hero 表，#122 复用 GFA audit，#124 不改数据库。

1. 从最终发布 commit 构建产物，保留旧二进制和配置；Admin 必须包含新 React build。
2. 如果 Tag migration 尚未应用，安排维护窗口、停止写入及所有旧 Game Backend、Game Collector、Admin 客户端，验证数据库备份可恢复。
3. 在工作站的仓库 `tools/` 用 `gofurry_migrator` 连接目标 `gfg`，先查状态，再迁到本版终点。下列占位符必须替换成经核对的私有 DSN，连接选项沿用已验证部署配置，不粘贴到日志或聊天。

   ```sh
   go tool goose -dir ../db/game/migrations postgres '<GFG_MIGRATOR_DSN>' status
   go tool goose -dir ../db/game/migrations postgres '<GFG_MIGRATOR_DSN>' up-to 20260916020000
   go tool goose -dir ../db/game/migrations postgres '<GFG_MIGRATOR_DSN>' status
   ```

   已应用目标版本时只核对状态；不要重放 SQL、修改 Goose 记录或重跑 baseline adoption。
   不要把共享开发的成功记录当作生产已经迁移的证据。
4. 用新 Game Backend 的私有命令重建被迁移清空的推荐；使用正常 `gofurry_app` runtime YAML：

   ```sh
   ./gf-game recommendations rebuild --config /path/to/server.yaml
   ```

   确认 `algorithm=similar-v2.4.0-hybrid-cbf`、`failed=0`。它不启动 HTTP、Collector 或 Redis。
   若此前已完成本次切换，按实际推荐缓存状态决定是否还需要重建。
5. 启动相容的 Game Backend / Collector / Admin，并在新 Nav Web 上线前部署支持 #112 的 Nav Backend；最后重建并切换 Nav Web。
6. 核对服务日志、健康检查、Tag 分类/Adult 判断、简介保存、推荐、Hero Fixed 和资源回退，再恢复访问。

Tag migration **不能通过 Goose Down 回滚**。旧物理列/表被删除，旧程序不能接回新 schema；恢复必须使用经过验证的迁移前备份和相容二进制。
历史 Analytics 不重写。已在 alpha.8 完成的 Managed Assets 初始 cutover 不再执行。
详见[数据库契约](../../contracts/database.md)及[已有开发迁移证据](../acceptance/issue-116-local-tag-domain.md)。

## 配置与构建

- #122 为可选配置，旧 YAML 没有 `scheduled_purge` 时保持关闭；只有确实要启用定时刷新才新增以下块。保留原来的 zone、凭据和 `main_host`：

  ```yaml
  external_services:
    cloud_ops:
      edgeone:
        scheduled_purge:
          enabled: true
          time: "05:30"
          timezone: "Asia/Shanghai"
  ```

  仅刷新配置的 EdgeOne `main_host`，不补跑、不自动 retry、不刷新 Cloudflare/整区。
  详见 [CloudOps 运维](../operations/admin-cloudops.md)。本次审计没有触发任何 purge。
- #112/#124 没有必须新增的 runtime 配置。保留现有 public/internal API 和资产线路配置。
- Nav Web 已使用 `.env` 的部署继续在 `apps/cn/nav-web` 执行 `./update.sh`，Compose 会自动读取它；只有选择 `.env.production` 文件名时才使用 `docker compose --env-file .env.production -f docker-compose.prod.yml up -d --build`。无需改名，也不从 example 覆盖已有文件。细节见[前端部署说明](../../apps/cn/nav-web/DEPLOYMENT.md)。
- 本地/CI 使用 Node 24，`npm ci` 自动运行 `nuxt prepare`。Docker 自行构建生产产物；不要发布测试 fixture server 或搬运测试容器的 `.output`。
- 仓库版本由 release tag 标识。Nav Web 是未发布的私有 npm 项目，没有 package version；Admin React 的 `0.0.0` 及服务 CLI 现有历史版本字符串不能用来证明部署了 alpha.9。记录构建 commit 与产物 checksum，本次不引入新的版本注入机制。
